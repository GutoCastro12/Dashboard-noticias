# 1. Resumo executivo

Este chat tratou da evolução de um dashboard interno chamado **"Radar de Risco — Emissores"**, construído para Gustavo Castro (Vinci Partners), cujo objetivo é monitorar risco de crédito de uma carteira de investimentos via notícias públicas, classificando eventos por emissor e gerando um ranking de risco atualizável periodicamente.

O chat começou a partir de um resumo de sessões anteriores (já compactado pelo sistema), que descrevia um projeto em produção parcial com pipeline Python, config YAML, template HTML/JS e deploy estático no Render via GitHub Actions. A partir desse ponto, quatro fases de trabalho foram conduzidas nesta conversa: **Fase 1** (diagnóstico de cobertura + exportação CSV/Excel/resumo), **Fase 2** (expansão da watchlist de 73 para 160 emissores + criação do subgrupo "Gestoras/Fundos"), **Fase 3** (cobertura internacional via SEC/EDGAR, tradução multilíngue, taxonomia própria de veículos/gestores) e **Fase 4** (diagnóstico e implementação parcial — Fase 4A — de auditoria CVM, keywords de rating multilíngues, exportações enriquecidas, validações e uma ferramenta de diagnóstico de fontes oficiais chamada `--probe-sources`).

Um padrão recorrente e estruturalmente importante neste chat é o seguinte ciclo: o assistente implementa uma fase → o usuário audita o pacote entregue com rigor técnico específico → identifica erros metodológicos ou de engenharia reais → o assistente corrige. Isso ocorreu em **três rodadas de correção formal** (uma para Fases 1+2, uma para Fase 3, uma para Fase 4A), cada uma delimitada por um documento extenso do usuário listando itens numerados. Essas correções não foram cosméticas: incluíram uma reclassificação metodológica central (subgrupo de emissor deve refletir a **natureza do emissor**, não o **instrumento** pelo qual a posição aparece na carteira), a correção do critério de elegibilidade ao EDGAR (de ~19 para 32 emissores elegíveis), a separação do campo `ticker` (cadastral) dos `aliases` (busca textual) para evitar falsos positivos, e a correção de um bug real na lógica de confiança de casamento da auditoria CVM (termos curtos como "BRF" e "TIM" quase geraram falsos positivos de alta confiança).

O estado mais recente conhecido neste chat é: a Fase 4A foi implementada, testada localmente (com fixtures para as chamadas de rede bloqueadas pelo sandbox) e ajustada três vezes a pedido do usuário até `--strict-groups` rodar com **0 erros e 0 warnings** em ambiente local. **Nada neste chat comprova que o código foi de fato enviado ao GitHub, que o GitHub Actions rodou, ou que o Render publicou a versão mais recente.** O próprio usuário reafirmou múltiplas vezes "não subi nada ainda" e pediu, na penúltima mensagem, a lista consolidada de arquivos a subir — o assistente entregou 6 arquivos (`config_risco.yaml`, `risk_dashboard.py`, `template_risco.html.j2`, `README.md`, `update_risk_dashboard.yml`, `requirements.txt`) como o pacote de produção.

Um ponto crítico de confiabilidade: todo o ambiente de trabalho é um sandbox efêmero (`/home/claude/risk-monitor/`), que é limpo entre sessões, e um diretório de saída persistente (`/mnt/user-data/outputs/radar-de-risco/`) que funciona como "última versão conhecida pelo assistente", mas **não é o repositório GitHub real**. Em pelo menos duas ocasiões, arquivos que existiam nesse diretório de saída (`README.md`, `fase2_candidatos_inclusao.csv`) não haviam sido efetivamente mostrados ao usuário via a ferramenta de apresentação de arquivos, e o usuário reclamou formalmente da ausência. Isso é uma lição operacional relevante para qualquer agente que continue este trabalho: **a existência de um arquivo no diretório de saída do assistente não implica que o usuário o recebeu.**

A rede do ambiente de execução bloqueia os domínios reais necessários para várias funcionalidades (`sec.gov`, `data.sec.gov`, `dados.cvm.gov.br`, `cmfchile.cl`, `bmv.com.mx`, `superfinanciera.gov.co`, `cnv.gov.ar`). Por isso, **o coletor EDGAR, a auditoria CVM e o probe de fontes oficiais nunca foram executados contra endpoints reais nesta conversa** — todos foram validados com fixtures/mocks construídos manualmente pelo assistente. Isso é aceitável como validação de lógica, mas não constitui prova de que o código funciona em produção. O usuário está ciente disso e pediu explicitamente que a validação real ocorra no GitHub Actions.

Nenhum scraper para CMF (Chile), CNBV/BMV (México) ou SIMEV (Colômbia) foi implementado — isso foi uma decisão explícita do usuário, condicionada ao resultado do `--probe-sources` rodado em ambiente com rede aberta (GitHub Actions). O coletor de agências de rating (S&P, Moody's, Fitch) também foi deliberadamente **não implementado**; a decisão foi reforçar palavras-chave multilíngues e confiar na imprensa com peso de confiança 0,99 para domínios de agências.

Os manuais LaTeX (português e espanhol, mencionados no resumo de sessão anterior como existentes em `/home/claude/doc/` e `/mnt/user-data/outputs/radar-de-risco/documentacao/`) **não foram atualizados nesta conversa** e foram repetidamente adiados para uma "Fase 4C" ainda não iniciada. Eles refletem uma estrutura desatualizada (anterior às Fases 2, 3 e 4A) e não devem ser tratados como fonte de verdade.

O principal ponto que o próximo agente precisa preservar é a regra metodológica central estabelecida e testada nesta conversa: **o subgrupo cadastral de um emissor (Empresas listadas / Não listadas / FIIs / Gestoras-Fundos) deve refletir a natureza do emissor monitorado, nunca o instrumento pelo qual a posição aparece na carteira** — e o mecanismo `applies_to` que impede que eventos da taxonomia corporativa pontuem veículos de investimento e vice-versa.

# 2. Objetivo do projeto e valor de negócio

O sistema é usado por **Gustavo Castro**, que trabalha na área de risco da **Vinci Partners** (gestora de investimentos brasileira). O dashboard suporta a **rotina de monitoramento de risco de crédito** de uma carteira de investimentos com exposição a mais de 1.100 emissores distintos (ações, dívida corporativa, fundos, FIIs, participações privadas), distribuídos principalmente entre Brasil, EUA, Chile, México, Colômbia e Argentina, com cauda em outros países.

O problema de negócio original (herdado do resumo de sessão anterior, não reexplicado em detalhe nesta conversa) é: identificar rapidamente notícias que sinalizam deterioração de risco de crédito para os emissores da carteira, sem depender de fontes pagas (Bloomberg/Reuters), usando um pipeline automatizado que roda em cron via GitHub Actions e publica um dashboard estático no Render.

Nesta conversa, o foco de negócio evoluiu para responder a uma pergunta concreta que o chefe de Gustavo fez: **"estou vendo poucas notícias — é porque não há eventos relevantes, ou porque a cobertura do dashboard ainda é limitada?"**. A resposta construída ao longo da Fase 1/2 foi que **era cobertura limitada**: a watchlist original de 73 emissores cobria apenas ~18,7% do financeiro da carteira (depois recalculado para 29,9% com metodologia unificada), e o universo elegível por materialidade (representação ≥ 0,1%) chegava a 177 emissores.

O que seria considerado sucesso, segundo o padrão estabelecido pelo próprio usuário ao longo das rodadas de correção, é: (a) cobertura ampliada e auditável por materialidade; (b) classificação cadastral metodologicamente correta (natureza do emissor, não instrumento); (c) separação clara entre cobertura oficial/reforçada (RI, reguladores) e cobertura ampla (imprensa geral) — nunca confundir ausência de RI com ausência de cobertura; (d) validações automáticas que bloqueiam o deploy quando há inconsistência cadastral real; (e) documentação que não afirma nada como "pronto" sem evidência.

Diferenciação objetivo técnico vs. de negócio:
- **Objetivo técnico**: pipeline de coleta (CVM/IPE, SEC/EDGAR, RSS internacionais) → classificação por taxonomia de eventos → atribuição por emissor → scoring → dashboard exportável.
- **Objetivo de negócio**: dar à área de risco da Vinci Partners visibilidade tempestiva e auditável sobre eventos de crédito relevantes em toda a carteira, incluindo a porção internacional, sem depender de terminal pago.

Stakeholders mencionados: Gustavo Castro (usuário direto) e seu "chefe" (mencionado como origem da pergunta que motivou a Fase 1; não nomeado).

# 5. Arquitetura e fluxo de dados

O fluxo de dados conhecido nesta conversa (a arquitetura completa do pipeline foi herdada de sessões anteriores; aqui foram adicionados/alterados estágios específicos):

```
FONTES
  ├─ CVM/IPE (Brasil)               → fetch_cvm_fatos()      [existente, confirmado varrer todo o dataset]
  ├─ SEC/EDGAR (EUA + estrangeiros
  │  com registro na SEC)           → fetch_edgar_filings()  [NOVO nesta conversa — Fase 3/4]
  ├─ RSS internacionais (11 feeds)  → fetch_custom_feeds()   [expandido nesta conversa — Fase 3]
  ├─ RI scraping (Tier 1 BR)        → fetch_ri_news_pages()  [existente, não alterado aqui]
  └─ Busca ampla / Google News      → fetch_all()             [existente, não alterado aqui]
        ↓
TRADUÇÃO (translate-then-classify)   → translate_articles(), detect_language()   [NOVO — Fase 3]
  entrada: artigo bruto (título, resumo, idioma detectado)
  saída: artigo com title_original/summary_original preservados + texto traduzido p/ pt
        ↓
CLASSIFICAÇÃO POR TAXONOMIA          → classify_article()   [existente; keywords ampliadas nesta conversa]
  entrada: artigo (traduzido ou original)
  saída: lista de event_ids casados
        ↓
ATRIBUIÇÃO POR EMISSOR               → detect_companies()   [existente, não alterado na lógica central]
        ↓
FILTRO DE APLICABILIDADE POR NATUREZA → event_applies_to()   [NOVO — Fase 3/4]
  entrada: evento + grupo cadastral do(s) emissor(es) citados
  saída: evento mantido só se aplicável à natureza do emissor
  ATENÇÃO: este filtro precisa ser aplicado tanto no Radar (build_evolution)
  quanto no feed de notícias (build_feed) — foi um bug real corrigido nesta conversa
        ↓
DEDUPLICAÇÃO                         → dedupe_articles()     [existente, não alterado aqui]
        ↓
PERSISTÊNCIA EM HISTÓRICO             → merge_into_history()  [ajustado para preservar language/title_original]
        ↓
SCORING / AGREGAÇÃO POR EMISSOR       → build_evolution()     [ajustado: scoring_mode, coverage_of()]
        ↓
RENDERIZAÇÃO (payload JSON → HTML)    → render via Jinja2 (template_risco.html.j2)
        ↓
EXPORTAÇÃO (client-side, no navegador)
  CSV / XLSX (gerador nativo) / Markdown (resumo diário)
        ↓
PUBLICAÇÃO ESTÁTICA NO RENDER (via GitHub Actions) — NÃO EXECUTADO NESTA CONVERSA
```

Riscos e invariantes por etapa (os identificados/reforçados nesta conversa):

- **Fontes → Coleta**: fonte oficial sem resultado deve gerar log informativo, nunca falha silenciosa (invariante reafirmado pelo usuário na Fase 4). O coletor EDGAR e a auditoria CVM seguem esse padrão (try/except com print de aviso, não exceção fatal), exceto quando é erro de **configuração** (`validate_sources`), que agora é fatal em modo estrito.
- **Tradução → Classificação**: a classificação **não pode depender exclusivamente da tradução** — por isso os termos multilíngues foram adicionados como rede de segurança. Se a tradução falhar (sem chave de API), o pipeline precisa seguir funcionando com o texto original.
- **Atribuição → Filtro de aplicabilidade**: este filtro deve ser aplicado em **todo lugar onde eventos por emissor são exibidos como "classificados"** — Radar e aba de Notícias. Aplicá-lo só em um lugar gera inconsistência visível ao usuário (foi exatamente o bug relatado na Fase 3→4).
- **Scoring**: `scoring_mode` do emissor (`normal` / `taxonomia_propria` / `monitoramento_limitado`) determina como o status final é calculado; gestoras/fundos com `taxonomia_propria` só recebem status Crítico/Atenção pelos eventos de veículo, nunca pelos corporativos.
- **Exportação**: não pode depender de CDN externo (SheetJS foi tentado e falhou por bloqueio de rede tanto no sandbox quanto, presumivelmente, em produção estática) — daí o gerador `.xlsx` nativo em JS puro.

A arquitetura **não está integralmente disponível nesta conversa** — partes como o motor de scoring/decaimento temporal detalhado, a lógica completa de deduplicação e a estrutura de `risk_history.json` foram tratadas como caixas-pretas já existentes, referenciadas mas não reexplicadas em profundidade neste chat.

# 7. Decisões técnicas e de produto

## DEC-01 — Subgrupo cadastral por natureza do emissor, não por instrumento

- Problema: a primeira versão da Fase 2 classificou o subgrupo (Empresas listadas / Não listadas / FIIs) a partir da coluna `Categoria` da base de posições (ex.: `CORPORATE BOND`, `AÇÃO (BRL)`), contaminando a classificação com o tipo de instrumento em vez da natureza do emissor.
- Decisão: subgrupo = natureza do emissor monitorado (companhia aberta, empresa fechada, fundo listado, gestora/veículo); instrumento da posição é irrelevante para essa classificação.
- Objetivo: evitar que companhias abertas internacionais (Ford, GM, Citigroup, Cemex, Ecopetrol) apareçam como "não listadas" só porque entraram na carteira via bond, e que SPEs privadas (florestais, Hospital Care) apareçam como "listadas" só porque entraram via ação ON.
- Justificativa: o subgrupo determina a taxonomia aplicável e o modo de cobertura; um erro aqui propaga para score, filtros e exportação.
- Alternativas consideradas: nenhuma alternativa foi discutida — foi tratado como correção de bug metodológico, não como escolha de design.
- Trade-offs: exige curadoria manual por emissor (ticker, bolsa, registro), não é derivável automaticamente da base de posições.
- Consequências: distribuição final mudou de 71 listadas/65 não-listadas para 105 listadas/31 não-listadas.
- Invariantes: nenhuma reclassificação futura deve usar `Categoria`/instrumento como critério de subgrupo.
- Status: IMPLEMENTADO_NO_REPOSITORIO / TESTADO_LOCALMENTE.
- Evidência: `validate_asset_classes` gera warning quando "não listada" tem ticker/bolsa (sinal de erro de instrumento) e quando "listada" não tem nenhum.
- O que verificar no repositório: se o `config_risco.yaml` real do GitHub já reflete essa classificação ou ainda tem a versão anterior.

## DEC-02 — Separar `ticker` (campo cadastral) de `aliases` (termos de busca textual)

- Problema: tickers curtos (F, C, GM, ET, MU, TD) inseridos como alias de busca casam com palavras comuns em manchetes, gerando falso positivo massivo.
- Decisão: `ticker` é campo cadastral (validação, exportação, EDGAR); `aliases` só contém termos seguros para casamento de texto.
- Objetivo: eliminar falsos positivos de atribuição de notícia a emissor.
- Justificativa: um teste no sandbox mostrou 48 tickers curtos indevidamente presentes nos aliases após uma reconstrução automática do cadastro.
- Trade-offs: exige lógica adicional (`has_stock_ticker`) para não perder a informação de ticker na validação/exportação mesmo sem usá-lo como termo de busca.
- Consequências: um bug intermediário fez o script de correção remover também aliases legítimos e não-curtos (BTG, PRIO, JBS, WEG, TIM) — corrigido restaurando os aliases originais e removendo só os tickers de fato curtos.
- Invariantes: nenhum termo com 4 caracteres ou menos deve entrar em `aliases`, salvo exceções documentadas (`alias_seguro()` na correção).
- Status: IMPLEMENTADO_NO_REPOSITORIO / TESTADO_LOCALMENTE.
- Evidência: teste mostrando `BTG Pactual aliases: ['BTG Pactual', 'BTG', 'BPAC11', 'BPAC3', 'BPAC5']` após a correção.
- O que verificar: revisar manualmente uma amostra do `config_risco.yaml` real para confirmar que nenhum ticker curto restou em `aliases`.

## DEC-03 — País/região = domicílio do emissor, nunca a praça de negociação

- Problema: um BDR negociado no Brasil (ex.: MercadoLibre) poderia ser erroneamente cadastrado como Brasil.
- Decisão: `country`/`region` refletem o domicílio do emissor monitorado, não o instrumento/praça.
- Objetivo: evitar mascarar a exposição internacional real da carteira.
- Justificativa: pedido explícito do usuário na correção da Fase 2 ("Se o ativo é BDR no Brasil, mas o emissor é estrangeiro, o país deve refletir o emissor, não automaticamente Brasil").
- Trade-offs: exige fallback explícito quando o domicílio não é conhecido — resolvido com o valor sentinela `"A revisar"` (ver DEC-04).
- Status: IMPLEMENTADO_NO_REPOSITORIO / TESTADO_LOCALMENTE.
- Evidência: MercadoLibre, StoneCo, Nubank e outros marcados com `revisar_pais` no dicionário de exceções de domicílio.
- O que verificar: se essas exceções de domicílio persistem corretamente no `config_risco.yaml` do repositório.

## DEC-04 — Nenhum fallback silencioso para "Brasil"; usar sentinela "A revisar"

- Problema: o payload e a exportação usavam `r.country || 'Brasil'`, o que mascararia erro de cadastro na expansão internacional.
- Decisão: fallback explícito para `"A revisar"`, com warning de validação.
- Justificativa: pedido explícito do usuário na correção da Fase 1/2.
- Status: IMPLEMENTADO_NO_REPOSITORIO / TESTADO_LOCALMENTE.
- Evidência: `validate_asset_classes` emite warning quando `country`/`region` está como `"A revisar"`.

## DEC-05 — Tiers por materialidade + conceito separado de "cobertura oficial prioritária"

- Problema: a regra de tier por materialidade geral não produz nenhum Tier 1 internacional (maior emissor internacional é Bunge, com 0,598% de representação — abaixo do corte de 1,0%).
- Decisão do usuário: manter a regra de tier por materialidade geral **sem forçar** Tier 1 internacional; criar um conceito **separado**, "cobertura oficial prioritária" = representação ≥ 0,3% (ou relevância qualitativa definida pela área), independente do tier.
- Objetivo: não distorcer os tiers só para "ter Tier 1 internacional", mas ainda assim ter um critério objetivo de priorização de fontes oficiais para a expansão internacional.
- Status: DECIDIDO_MAS_NAO_IMPLEMENTADO no código como campo formal — foi usado como critério de análise no diagnóstico (`fase4_cobertura_oficial.csv`), mas não há evidência de um campo/flag `cobertura_oficial_prioritaria` persistido no cadastro.
- O que verificar: se esse conceito precisa virar um campo explícito no `config_risco.yaml` ou permanece como critério de análise ad hoc.

## DEC-06 — Gestoras/Fundos: subgrupo próprio, com taxonomia ancorada em normas reais

- Problema: veículos de investimento (SPX, Kapitalo, JGP, Blackstone etc.) não são emissores de risco de crédito corporativo tradicional, mas representam risco de veículo/gestor que precisa ser monitorado com taxonomia própria.
- Decisão: criar subgrupo `gestora_fundo`, com campos `vehicle_kind` e `tratamento`, e uma taxonomia de 11 eventos ancorados em **SEC Rule 22e-4 (17 CFR 270.22e-4)**, **ESMA (AIFMD II/UCITS — LMTs)** e **IOSCO (terminação de fundos)** — não inventados.
- Objetivo: evitar que "recuperação judicial" ou "covenant breach" (eventos corporativos) sejam lidos como risco de um fundo, e vice-versa.
- Mecanismo: campo `applies_to` em cada evento da taxonomia, checado por `event_applies_to()`.
- Status: IMPLEMENTADO_NO_REPOSITORIO / TESTADO_LOCALMENTE. Testes cruzados confirmaram: Kapitalo + "recuperação judicial" → ignorado; Kapitalo + "suspensão de resgates" → pontua Crítico; Petrobras + "recuperação judicial" → pontua Crítico; Petrobras + "suspensão de resgates" → ignorado.
- Evolução do `scoring_mode`: começou como `monitoramento_limitado` (Fase 2/3 inicial, sem taxonomia própria implementada) e evoluiu para `taxonomia_propria` assim que os 11 eventos foram codificados (Fase 3, após o usuário apontar contradição no texto de exportação).
- O que verificar: se `SCORING_MODES = {"normal", "taxonomia_propria", "monitoramento_limitado"}` está sincronizado entre validação e uso real no scoring.

## DEC-07 — Critério de elegibilidade ao EDGAR: relação com a SEC, não país de domicílio

- Problema: a primeira versão usava `country in ("EUA", "Canadá") and ticker`, que dava apenas 19 emissores elegíveis e deixava de fora companhias estrangeiras com ações/ADR registrados na SEC (Bunge/Suíça, Cemex/México, Ecopetrol/Colômbia, MercadoLibre/Uruguai, StoneCo e Nubank/Brasil, YPF e Telecom Argentina/Argentina, Millicom/Luxemburgo).
- Decisão: `edgar_eligible(company)` = tem `cik` OU `official.sec: true` OU listagem NYSE/Nasdaq OU (ticker + domicílio norte-americano).
- Objetivo: refletir corretamente quem de fato reporta à SEC.
- Justificativa: apontado pelo usuário após auditoria explícita, citando 10 exemplos concretos de emissores que ficavam de fora indevidamente.
- Consequências: 19 → 32 emissores elegíveis; número documentado em `FASE3_INTERNACIONAL.md`/`FASE4A_IMPLEMENTACAO.md` foi reconciliado para 32.
- Status: IMPLEMENTADO_NO_REPOSITORIO / TESTADO_LOCALMENTE (fixture; nunca contra `sec.gov` real).
- Invariante nova de validação: emissor com listagem NYSE/Nasdaq mas fora do EDGAR → warning; emissor com `cik`/`official.sec` mas fora do EDGAR → **erro** (inconsistência de regra).

## DEC-08 — Estratégia de tradução: translate-then-classify + rede de segurança multilíngue

- Problema: a taxonomia de eventos está em português; notícias internacionais em inglês/espanhol precisam ser classificadas.
- Decisão: traduzir **apenas título e resumo curto** (não o corpo completo) para português antes de classificar, preservando `title_original`/`summary_original` e o link original.
- Justificativa reformulada a pedido do usuário: inicialmente o assistente descreveu isso citando "evidência recente" da literatura sem fonte concreta; o usuário pediu para reescrever como **decisão técnica interna** (padronizar classificação em um idioma só, reduzir perda de eventos), não como afirmação científica.
- Achado de teste que gerou uma decisão adicional: se a tradução falhar (sem chave de API, cota esgotada), a classificação baseada só em termos em português perderia silenciosamente toda notícia internacional. Por isso foram adicionados +88 termos em inglês/espanhol aos eventos corporativos mais materiais e aos eventos de veículo, como rede de segurança.
- Status: IMPLEMENTADO_NO_REPOSITORIO / TESTADO_LOCALMENTE (sem chamada real ao Gemini).
- Evidência: "Ford Motor downgraded by rating agency" classificado corretamente mesmo sem tradução, graças aos termos em inglês.

## DEC-09 — Coletor de agências de rating deliberadamente adiado

- Problema: S&P, Moody's e Fitch não oferecem RSS/API pública estável; conteúdo profundo é pago.
- Decisão do usuário: não construir scraper dedicado agora; reforçar apenas as palavras-chave multilíngues (CreditWatch, Rating Watch, *revisión a la baja*, *clasificación de riesgo* etc.) e manter peso de confiança 0,99 para os domínios de agências (incluindo locais: Feller Rate, Humphreys, HR Ratings, Verum, BRC, Value & Risk, Austin, SR Rating).
- Status: DECIDIDO_MAS_NAO_IMPLEMENTADO (coletor) / IMPLEMENTADO_NO_REPOSITORIO (keywords e `source_trust`).
- O que verificar: se um coletor dedicado deve entrar em pauta em fase futura.

## DEC-10 — Argentina excluída da Fase 4A de scraping regulatório

- Problema: os 2 emissores argentinos da watchlist (YPF, Telecom Argentina) já são cobertos via EDGAR (ADRs na NYSE); a fonte local (CNV/AIF) tem histórico de instabilidade relatado.
- Decisão do usuário: confirmar exclusão da Argentina da Fase 4A; documentar como coberta via EDGAR; revisar apenas se entrar emissor argentino relevante sem essa cobertura.
- Status: DECIDIDO_MAS_NAO_IMPLEMENTADO (nenhum scraper AIF foi cogitado para implementação futura imediata) / documentado.

## DEC-11 — `--probe-sources`: medir antes de implementar scraper, distinguindo bloqueio de ambiente

- Problema: o ambiente de desenvolvimento (sandbox) não alcança os portais dos reguladores latino-americanos; implementar scraper sem essa validação seria "scraper frágil" (termo do próprio usuário).
- Decisão: criar um comando de diagnóstico que **mede sem coletar** — status HTTP, tipo de conteúdo, presença de RSS, indício de JS, sinal de anti-bot, latência — a ser rodado no GitHub Actions (rede aberta).
- Achado crítico corrigido nesta mesma implementação: a primeira execução real (mesmo no sandbox) reportou "anti-bot" para as 15 URLs medidas — o que era **falso**: o bloqueio vinha do proxy de egresso do próprio ambiente (`x-deny-reason` / "not in allowlist"), não das fontes. Corrigido adicionando o campo `bloqueio_ambiente`, checado com precedência sobre `anti_bot`.
- Status: IMPLEMENTADO_NO_REPOSITORIO / TESTADO_LOCALMENTE (mock + execução real que só mediu bloqueio de ambiente).
- Invariante: um probe que confunde bloqueio de ambiente com anti-bot real da fonte é **pior que nenhum diagnóstico**, porque a decisão da Fase 4B depende dele.

## DEC-12 — `validate_docs` só se aplica a documentação de produção, não a documentos de fase/plano

- Problema: a primeira versão de `validate_docs` sinalizava como "desatualizados" os próprios documentos de fase (`FASE4A_IMPLEMENTACAO.md`, `FASE4_PLANO.md`), que citam números antigos **de propósito**, para registrar o que foi corrigido.
- Decisão: excluir da checagem arquivos cujo nome case com `_DOC_HISTORICOS = re.compile(r"(FASE\d|PLANO|DIAGNOSTICO|CHANGELOG|HISTORICO)", re.I)`.
- Justificativa: pedido explícito do usuário — "isso não parece ser erro metodológico, mas contradiz a frase '0 erros e 0 warnings'".
- Status: IMPLEMENTADO_NO_REPOSITORIO / TESTADO_LOCALMENTE — confirmado rodar com 0 warnings mesmo com os documentos de fase presentes no diretório.

## DEC-13 — ERRO de `validate_sources` deve bloquear o deploy em modo estrito

- Problema: mensagens `ERRO` de `validate_sources` eram logadas mas não interrompiam a execução.
- Decisão: em `--strict-groups`, `ERRO` de fonte gera `SystemExit` (exit code 1); sem a flag, apenas loga e segue.
- Status: IMPLEMENTADO_NO_REPOSITORIO / TESTADO_LOCALMENTE — testado injetando um feed sem URL, confirmando `exit=1` com a flag e `exit=0` sem ela.

## DEC-14 — Auditoria CVM: comprimento do termo tem precedência sobre a origem (nome vs. alias) na confiança do match

- Problema: a primeira versão de rastreabilidade do match classificava a confiança pela **origem** do termo casado (nome do emissor vs. alias), o que permitia que "BRF" (nome do emissor, 3 caracteres) casando dentro de "BRF FOODS INDUSTRIA LTDA" recebesse confiança **média**, quando deveria ser **baixa** por risco de homônimo.
- Decisão: inverter a regra — qualquer termo casado com menos de 6 caracteres recebe `tipo_match="revisar"` e `confianca_match="baixa"`, independentemente de ser o nome do emissor ou um alias.
- Status: IMPLEMENTADO_NO_REPOSITORIO / TESTADO_LOCALMENTE — confirmado com fixture que "BRF" e "TIM Brasil" (casando com "TIM PARTICIPACOES REGIONAL LTDA") corretamente caem em `revisar`/`baixa`.

## DEC-15 — Gerador de `.xlsx` nativo (ZIP+XML em JS puro), sem dependência de CDN

- Problema: a primeira tentativa de exportação Excel usou SheetJS via CDN (`cdn.sheetjs.com`), que falhou no sandbox por bloqueio de rede (domínio fora da allowlist); uma segunda tentativa com `cdnjs.cloudflare.com` também falhou pelo mesmo motivo.
- Decisão: implementar um gerador de `.xlsx` nativo em JavaScript (ZIP "stored", sem compressão, com CRC32 calculado à mão; XML mínimo de `[Content_Types].xml`, `workbook.xml`, `worksheet` etc.), sem nenhuma biblioteca externa.
- Justificativa: um site estático não deveria depender de CDN externo para uma funcionalidade básica de exportação — risco de quebra silenciosa em produção.
- Status: IMPLEMENTADO_NO_REPOSITORIO / TESTADO_LOCALMENTE — validado abrindo o arquivo gerado com `openpyxl` (Python), incluindo verificação de 6 abas, tipos de dados corretos (números como números).

# 8. Regras de negócio e invariantes

- **Atribuição de eventos por emissor**: um evento só é atribuído a um emissor se o texto casar com o nome ou um alias seguro (≥5 caracteres, salvo exceções documentadas de tickers de padrão de bolsa). Motivo: falsos positivos de tickers curtos já causaram problema real nesta conversa.
- **Separação instrumento × emissor**: o subgrupo cadastral nunca deve ser derivado da categoria/instrumento da posição na carteira. Motivo: é a correção metodológica central desta conversa (DEC-01).
- **Eventos pontuáveis por natureza do emissor (`applies_to`)**: eventos corporativos tradicionais (recuperação judicial, covenant breach, rebaixamento de rating etc.) não pontuam Gestoras/Fundos; eventos de veículo (suspensão de resgates, side pocket, liquidação, key person risk etc.) não pontuam companhias. Fraude, intervenção regulatória e suspensão de negociação valem para ambos os grupos (eventos "universais"). Motivo: risco de veículo/gestor é conceitualmente diferente de risco corporativo operacional.
- **Aplicação consistente do filtro de aplicabilidade**: o filtro `applies_to` deve valer tanto no cálculo de score (Radar) quanto na exibição de "notícias classificadas" (feed). Motivo: bug real relatado pelo usuário — o Radar filtrava corretamente, mas o feed ainda exibia eventos não aplicáveis como "classificados válidos".
- **País/região = domicílio do emissor**: nunca a praça de negociação do instrumento. Motivo: BDRs e ADRs mascarariam a exposição internacional real se o país fosse herdado da praça.
- **Nenhum fallback geográfico silencioso**: ausência de país/região vira `"A revisar"` com warning, nunca `"Brasil"` por default. Motivo: mascarar erro de cadastro na expansão internacional.
- **Cobertura ampla é o piso de todo emissor; ausência de RI não é ausência de cobertura**: regra reafirmada múltiplas vezes pelo usuário. A distinção entre `coverage = "ampla"` e `coverage = "oficial/reforçada"` deve ser preservada em toda comunicação (docs, dashboard, exportação).
- **Fonte oficial sem resultado gera log informativo, nunca falha silenciosa**: invariante geral de engenharia reafirmada na Fase 4.
- **Tier por materialidade geral não deve ser forçado para produzir Tier 1 internacional**: se nenhum emissor internacional atinge o corte, não há Tier 1 internacional — usar o conceito separado de "cobertura oficial prioritária" em vez de distorcer os tiers (DEC-05).
- **Documentação não pode citar número desatualizado de emissores, fontes ou cobertura** — mas essa checagem só vale para documentos de **produção** (README, manuais); documentos históricos de fase/plano têm exclusão explícita, porque neles a citação ao número antigo é parte do registro histórico (DEC-12).
- **Erro de configuração de fonte bloqueia o deploy em modo estrito** — não deve ser apenas logado (DEC-13).
- **Confiança de match em auditorias automatizadas deve considerar o comprimento do termo casado, não sua origem** — termos curtos são a principal fonte de falso positivo por homônimo, independentemente de serem o nome do emissor ou um alias (DEC-14).
- **Nenhum scraper deve ser escrito sem validação de viabilidade técnica real** — o `--probe-sources` existe justamente para não repetir, em CMF/BMV/SIMEV, o padrão de "scraper frágil". Instrução explícita do usuário: não implementar scraper real antes do resultado do probe.

# 14. Tentativas que deram errado ou foram revertidas

- **Tentativa**: usar SheetJS via CDN (`cdn.sheetjs.com`, depois `cdnjs.cloudflare.com`) para gerar Excel na exportação.
  Por que parecia razoável: é a biblioteca padrão de mercado para gerar `.xlsx` em JavaScript.
  Por que estava errado: ambos os domínios estão fora da allowlist de rede do ambiente (e presumivelmente também seriam um ponto de falha em produção estática, que não deveria depender de CDN externo para uma funcionalidade básica).
  Impacto: exportação em Excel caía silenciosamente para CSV como fallback.
  Correção: gerador de `.xlsx` nativo em JS puro (ZIP + XML manual, CRC32 calculado à mão), sem nenhuma dependência externa.
  Lição geral: qualquer funcionalidade client-side de um site estático deve evitar dependência de CDN, e o ambiente de teste local nem sempre reflete as mesmas restrições de produção — mas neste caso a restrição do sandbox coincidiu com uma preocupação legítima de robustez em produção.

- **Tentativa**: classificar subgrupo cadastral a partir da coluna `Categoria` (instrumento) da base de posições, na primeira versão da Fase 2.
  Por que parecia razoável: era a informação mais direta disponível na base de dados exportada da carteira.
  Por que estava errado: instrumento ≠ natureza do emissor (um bond corporativo pode ter emissor listado; uma ação ON pode ser participação privada).
  Impacto: dezenas de emissores classificados incorretamente (Ford, GM, Citigroup como "não listadas"; SPEs florestais como "listadas").
  Correção: reclassificação manual curada por emissor, com regra explícita documentada no topo do `config_risco.yaml`.
  Lição geral: nunca inferir uma classificação cadastral estrutural a partir de um campo transacional/contábil sem checagem cruzada (ticker, bolsa, registro).

- **Tentativa**: critério de elegibilidade EDGAR baseado em `country in ("EUA", "Canadá")`.
  Por que parecia razoável: parecia intuitivo que só emissores "americanos" reportassem à SEC.
  Por que estava errado: companhias estrangeiras com ações/ADR registrados na SEC também arquivam no EDGAR, independentemente do domicílio.
  Impacto: 13 emissores elegíveis (32-19) ficavam de fora da cobertura oficial sem necessidade.
  Correção: `edgar_eligible()` baseado em `cik`/`official.sec`/listagem NYSE-Nasdaq/ticker+domicílio.
  Lição geral: "elegibilidade a um regulador" deve ser modelada pela relação jurídica/de registro com aquele regulador, não por proxy geográfico.

- **Tentativa**: pesquisar viabilidade técnica de CMF/BMV/SIMEV e agências de rating via `launch_extended_search_task` no início da Fase 4.
  Por que parecia razoável: era a mesma abordagem usada com sucesso na Fase 3 para levantar a matriz de fontes internacionais.
  Por que não avançou: **o usuário recusou explicitamente essa chamada de ferramenta** (`tool call declined`).
  Impacto: o diagnóstico da Fase 4 teve que ser feito só com dados locais (watchlist, config existente), sem validação técnica externa dos endpoints — o próprio assistente sinalizou essa limitação no plano entregue.
  Correção/mitigação: criação do `--probe-sources` como forma de obter essa validação depois, rodando no ambiente correto (GitHub Actions).
  Lição geral: quando pesquisa externa é recusada, o agente deve ser explícito sobre a lacuna de informação resultante, em vez de prosseguir como se tivesse validado algo que não validou.

- **Tentativa**: primeira versão do `--probe-sources`, sem distinguir bloqueio de ambiente de anti-bot real.
  Por que parecia razoável: status HTTP 403 é comumente associado a bloqueio anti-bot.
  Por que estava errado: no ambiente do assistente, 403 vinha do próprio proxy de egresso (allowlist de rede), não das fontes reais.
  Impacto: um diagnóstico "todas as fontes têm anti-bot" seria uma conclusão falsa e enganosa para decidir a Fase 4B.
  Correção: campo `bloqueio_ambiente`, detectado por header `x-deny-reason` ou padrões de texto como "not in allowlist", checado com precedência sobre `anti_bot`.
  Lição geral: uma ferramenta de diagnóstico precisa ser desenhada considerando as limitações do próprio ambiente onde ela roda primeiro, antes de rodar no ambiente-alvo.

- **Tentativa**: primeira versão da rastreabilidade de match da auditoria CVM, classificando confiança por origem do termo (nome do emissor vs. alias).
  Por que parecia razoável: pareceria mais confiável um termo ser "o próprio nome do emissor" do que um alias qualquer.
  Por que estava errado: um nome de emissor curto (ex.: "BRF", "TIM Brasil" via alias "TIM") é tão suscetível a homônimo quanto um alias curto — o fator decisivo é o **comprimento** do termo casado, não sua origem.
  Impacto: "BRF" casando com "BRF FOODS INDUSTRIA LTDA" teria sido reportado como confiança média, mascarando um provável falso positivo.
  Correção: regra reordenada para que comprimento < 6 caracteres sempre gere `revisar`/`baixa`, independentemente da origem.
  Lição geral: em regras de match textual, o comprimento/especificidade do termo é geralmente mais preditivo de confiabilidade do que sua categoria de origem.

- **Tentativa (padrão recorrente, não um evento único)**: apresentar arquivos como "entregues" só por existirem no diretório de saída do assistente, sem chamar a ferramenta de apresentação de arquivos para o usuário.
  Por que parecia razoável: o arquivo estava fisicamente presente e mencionado em texto.
  Por que estava errado: o usuário só recebe/visualiza o que é explicitamente apresentado; documentar "arquivo X foi gerado" no texto da resposta não substitui a apresentação real.
  Impacto: usuário reclamou formalmente da ausência de `README.md` e `fase2_candidatos_inclusao.csv` em pelo menos uma rodada.
  Correção: nas rodadas seguintes, o assistente passou a reconferir explicitamente a lista de arquivos existentes e apresentar todos os relevantes.
  Lição geral: para este tipo de fluxo de trabalho, a lista de arquivos efetivamente entregues ao usuário deve ser tratada como um subconjunto explícito e auditável dos arquivos gerados, nunca inferida.

# 20. Glossário do projeto

- **Emissor**: entidade (companhia, fundo, gestora) cujo risco de crédito é monitorado — distinto do "instrumento" pelo qual a posição aparece na carteira.
- **Subgrupo / asset_class**: classificação cadastral do emissor por natureza — `listada` (Empresas listadas), `nao_listada` (Não listadas / PE / Crédito), `fii` (FIIs), `gestora_fundo` (Gestoras/Fundos).
- **Tier**: nível de materialidade do emissor na carteira — T1 (≥1,0%), T2 (≥0,3%), T3 (≥0,1%), definido por representação financeira.
- **Cobertura oficial prioritária**: conceito separado do tier — emissor com representação ≥0,3% (ou relevância qualitativa da área) recebe prioridade de fonte oficial, independentemente do tier.
- **Cobertura ampla**: monitoramento por imprensa/notícias públicas — piso de cobertura de todo emissor.
- **Cobertura oficial/reforçada**: monitoramento direto via RI, regulador ou sistema de filing (CVM/IPE, SEC/EDGAR).
- **`applies_to`**: campo de cada evento da taxonomia que define a quais grupos de ativos (`listed_companies`, `nao_listada`, `fii`, `gestora_fundo`) aquele evento se aplica.
- **`scoring_mode`**: modo de pontuação do emissor — `normal` (taxonomia corporativa padrão), `taxonomia_propria` (só eventos de veículo/gestor), `monitoramento_limitado` (trava manual: coleta e exibe, mas não classifica).
- **`vehicle_kind`**: subtipo de um emissor do grupo Gestoras/Fundos — gestora, fundo, fundo_listado, veiculo_offshore, fundo_interno, fundo_terceiros.
- **Translate-then-classify**: estratégia de traduzir título/resumo para português antes de classificar o evento, mantendo o texto original preservado.
- **Rede de segurança multilíngue**: palavras-chave em inglês/espanhol adicionadas aos eventos mais materiais para que a classificação funcione mesmo se a tradução falhar.
- **`edgar_eligible()`**: função que determina se um emissor deve ser buscado no coletor SEC/EDGAR (por `cik`, `official.sec`, listagem NYSE/Nasdaq, ou ticker+domicílio norte-americano).
- **`--audit-cvm`**: comando que audita quais emissores brasileiros são efetivamente filiantes no dataset IPE da CVM.
- **`--probe-sources`**: comando de diagnóstico que mede a acessibilidade técnica de fontes oficiais (status HTTP, RSS, JS, anti-bot) sem coletar dados.
- **`bloqueio_ambiente`**: sinal específico do probe que indica que a indisponibilidade de uma fonte é causada pelo ambiente de execução (proxy/allowlist), não pela fonte em si.
- **IPE**: Informações Periódicas e Eventuais, dataset público da CVM usado para identificar fatos relevantes e companhias filiantes.
- **Fato relevante**: comunicado obrigatório de companhias abertas no Brasil, equivalente ao "material event" americano (Form 8-K/6-K).
- **`--strict-groups`**: flag do pipeline que torna erros de validação fatais (aborta a execução).
- **`--reclassify`**: flag que reprocessa todo o histórico com as regras/keywords atuais.
- **`--backfill`**: flag que semeia o histórico com janela de busca ampliada, usada normalmente na primeira execução.
